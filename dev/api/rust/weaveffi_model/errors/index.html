The shared error naming policy.

The error model (which domains exist, which codes they carry, which module owns them) lives in the model as ErrorBinding. This module holds only the idiomatic naming rules every backend applies to those names, centralized so no target drifts into KEY_NOT_FOUNDError (raw SCREAMING_SNAKE with a naive Error suffix) or KitchenErrorsError while another emits keyNotFound.

Backends pick the suffix that matches their ecosystem (Error or Exception) and case-convert each code’s name through the helpers below. Every generator names domain and code types through type_name (or exception_type_name), never by hand.

Functions§

exception_type_name
Exception-branded type name for an error domain or code, for targets whose idiomatic errors are exceptions rather than *Error types: type_name with the Exception suffix (KvError -> KvException, Failure -> FailureException, a bare Error -> Exception).
pascal
PascalCase form of a raw error code name, with no suffix. KEY_NOT_FOUND -> KeyNotFound. Use for languages whose error variants are nested types or cases (Kotlin sealed subclasses, Swift enum cases) rather than standalone *Error classes.
type_name
PascalCase plus exactly one suffix, never doubled.
