# IDL Reference

WeaveFFI consumes a declarative IDL (interface definition language) that
describes modules, types, and functions. YAML, JSON, and TOML are all
supported; this reference uses YAML throughout. This page documents schema
version `0.9.0`, the only version the current tools accept.

Every YAML block on this page is a complete document that passes
`weaveffi validate`, except the blocks whose first line is `# rejected:`,
which show exactly what the validator refuses and which error code it
reports.

## Editor autocomplete (JSON Schema)

WeaveFFI ships a JSON Schema for the IDL. To get autocomplete and validation
in editors that support the [YAML Language Server](https://github.com/redhat-developer/yaml-language-server)
(VS Code, Neovim, Helix, and others), add this header comment to the top of
your YAML file:

```yaml
# yaml-language-server: $schema=./weaveffi.schema.json
```

The schema is generated by `weaveffi schema --format json-schema`, and a copy
is checked in at [`weaveffi.schema.json`](https://github.com/weavefoundry/weaveffi/blob/main/weaveffi.schema.json)
in the repository root.

## Top-level structure

The shape of an IDL document, with placeholder ellipses for nested arrays
and objects:

```text
# yaml-language-server: $schema=./weaveffi.schema.json
version: "0.9.0"
modules:
  - name: my_module
    doc: "..."
    structs: [...]
    enums: [...]
    interfaces: [...]
    callback_interfaces: [...]
    functions: [...]
    errors: { ... }
    modules: [...]
```

The document describes only the API. Package identity and per-generator
options live in a `weaveffi.toml` next to it; see
[Project Configuration](../guides/config.md). Every object in the schema
rejects unknown keys, so a stray `package:` block, a leftover
`callbacks:` list, or a misspelled field fails to parse instead of being
silently ignored.

A complete, validating example lives at the bottom of this page in the
[Complete example](#complete-example) section.

| Field     | Type            | Required | Description                                                          |
|-----------|-----------------|----------|----------------------------------------------------------------------|
| `version` | string          | yes      | Schema version; only the current version (`"0.9.0"`) is accepted     |
| `modules` | array of Module | yes      | One or more modules                                                  |

### Module

| Field                 | Type                        | Required | Description                                                                     |
|-----------------------|-----------------------------|----------|---------------------------------------------------------------------------------|
| `name`                | string                      | yes      | Identifier used as a namespace segment and C symbol component (e.g. `kv`)       |
| `doc`                 | string                      | no       | Documentation for the module as a whole                                         |
| `functions`           | array of Function           | no       | Free functions exported by this module                                          |
| `interfaces`          | array of Interface          | no       | Reference-counted object types (see [Interfaces](#interfaces))                  |
| `callback_interfaces` | array of CallbackInterface  | no       | Method sets the consumer implements (see [Callback interfaces](#callback-interfaces)) |
| `structs`             | array of Struct             | no       | Record (value) types                                                            |
| `enums`               | array of Enum               | no       | C-style or algebraic enums                                                      |
| `errors`              | ErrorDomain                 | no       | The module's error domain (see [Error domain](#error-domain))                   |
| `modules`             | array of Module             | no       | Nested submodules (see [Nested modules](#nested-modules))                       |

### Function

| Field         | Type           | Required | Description                                                                                                        |
|---------------|----------------|----------|--------------------------------------------------------------------------------------------------------------------|
| `name`        | string         | yes      | Function identifier                                                                                                |
| `params`      | array of Param | no       | Ordered input parameters; defaults to none (`params: []` and omitting the key are equivalent)                       |
| `return`      | TypeRef        | no       | Return type; omit for a function that returns nothing                                                              |
| `doc`         | string         | no       | Documentation string                                                                                               |
| `throws`      | bool           | no       | Report typed domain errors (default `false`); requires an error domain in scope (see [Error domain](#error-domain)) |
| `async`       | bool           | no       | Lower to an asynchronous launcher plus completion callback (default `false`)                                       |
| `cancellable` | bool           | no       | Accept a cancel token (only meaningful with `async: true`)                                                          |
| `deprecated`  | string         | no       | Deprecation message propagated to every generated binding                                                          |

The same shape describes an interface's constructors, methods, and statics,
and a callback interface's methods, with the restrictions noted in their
sections.

### Param

| Field  | Type    | Required | Description                                                          |
|--------|---------|----------|----------------------------------------------------------------------|
| `name` | string  | yes      | Parameter name                                                       |
| `type` | TypeRef | yes      | Parameter type                                                       |
| `doc`  | string  | no       | Documentation string (see [Documentation comments](#documentation-comments)) |

### What schema 0.9.0 removed

Schema 0.9.0 accompanies ABI revision 2 and drops the pre-1.0 spellings
below. There is no compatibility shim; the parser rejects each with a
message pointing at its replacement.

| Removed                             | Replacement                                                                                                  |
|-------------------------------------|--------------------------------------------------------------------------------------------------------------|
| `handle`, `handle<T>` types         | Declare an [interface](#interfaces) and reference it by name; objects are reference counted by the producer  |
| `&str`, `&[u8]` types               | `string` and `bytes`; parameters are always borrowed views at the ABI, so the borrowed spellings said nothing |
| `Param.mutable`                     | Removed; no type crosses the boundary by mutable reference                                                   |
| `Function.since`                    | Use `deprecated:` text when a function is on its way out                                                    |
| module-level `callbacks:`           | A [callback interface](#callback-interfaces) with one method                                                  |
| module-level `listeners:`           | A callback interface passed to a `subscribe`-style method on an interface                                    |

## Package metadata

The IDL carries no package metadata. The name, version, and other
distribution identity stamped into every generated ecosystem manifest
(`package.json`, `pyproject.toml`, `*.gemspec`, `*.csproj`, `pubspec.yaml`,
`Package.swift`, `go.mod`, `settings.gradle.kts`, `CMakeLists.txt`) come
from the `[package]` table of the `weaveffi.toml` beside the definition:

```toml
[package]
name = "kvstore"
version = "1.0.0"
description = "An embedded key-value store API."
license = "MIT"
authors = ["WeaveFoundry <hello@weavefoundry.dev>"]
repository = "https://github.com/weavefoundry/weaveffi"
```

See [Project Configuration](../guides/config.md#package) for the schema and
the per-ecosystem name resolution rules.

## Type syntax

A `TypeRef` is written as a string. The grammar is small:

| Syntax     | Meaning                                                       |
|------------|---------------------------------------------------------------|
| `i32`, `string`, ... | A [primitive](#primitive-types)                          |
| `Name`     | A user type: struct, enum, interface, or callback interface, by bare or dot-qualified name |
| `T?`       | [Optional](#optional-types)                                   |
| `[T]`      | [List](#list-types)                                           |
| `{K:V}`    | [Map](#map-types)                                             |
| `iter<T>`  | [Lazy iterator](#iterator-types), returns only                |

The parser reads outside in: `[Contact?]` is a list of optional contacts,
`[Contact]?` an optional list. Quote anything that YAML would otherwise
interpret (`"string?"`, `"[i32]"`, `"{string:i32}"`).

## Primitive types

Every primitive is valid in parameters, returns, fields, and every composite
position.

| Type     | Description                     | Example value |
|----------|---------------------------------|---------------|
| `i8`     | Signed 8-bit integer            | `-12`         |
| `i16`    | Signed 16-bit integer           | `-1000`       |
| `i32`    | Signed 32-bit integer           | `-42`         |
| `i64`    | Signed 64-bit integer           | `9000000000`  |
| `u8`     | Unsigned 8-bit integer          | `200`         |
| `u16`    | Unsigned 16-bit integer         | `60000`       |
| `u32`    | Unsigned 32-bit integer         | `300`         |
| `u64`    | Unsigned 64-bit integer         | `18000000000` |
| `f32`    | 32-bit floating point           | `1.5`         |
| `f64`    | 64-bit floating point           | `3.14`        |
| `bool`   | Boolean                         | `true`        |
| `string` | UTF-8 string                    | `"hello"`     |
| `bytes`  | Byte buffer                     | binary data   |

`string` and `bytes` are borrowed for the duration of a call when passed in
(the producer copies what it keeps) and owned by the receiver when returned
(the consumer frees them with `weaveffi_free_string` or
`weaveffi_free_bytes`). See [Memory and Error Model](memory-error.md).

`[u8]` is accepted and canonicalizes to `bytes` at parse time: the two
encode identically inside a value buffer, and `bytes` is what a Rust
producer's `Vec<u8>` maps to.

> **Note on JavaScript and Wasm:** 64-bit integers (`i64`, `u64`) surface as
> `BigInt` in the Node and WebAssembly backends; every narrower integer and
> the floats surface as `number`.

### Primitive examples

```yaml
version: "0.9.0"
modules:
  - name: primitives
    functions:
      - name: add
        params:
          - { name: a, type: i32 }
          - { name: b, type: i32 }
        return: i32

      - name: scale
        params:
          - { name: value, type: f64 }
          - { name: factor, type: f64 }
        return: f64

      - name: count
        params:
          - { name: limit, type: u32 }
        return: u32

      - name: timestamp
        return: i64

      - name: is_valid
        params:
          - { name: token, type: string }
        return: bool

      - name: echo
        params:
          - { name: message, type: string }
        return: string

      - name: compress
        params:
          - { name: data, type: bytes }
        return: bytes
```

## Struct definitions

Structs define composite value types with named, typed fields. Define them
under the `structs` key of a module, then reference them by name in function
signatures and other type positions.

### Struct schema

| Field        | Type           | Required | Description                                          |
|--------------|----------------|----------|------------------------------------------------------|
| `name`       | string         | yes      | Struct name (e.g. `Contact`)                         |
| `doc`        | string         | no       | Documentation string                                 |
| `deprecated` | string         | no       | Deprecation message applied to the generated type    |
| `fields`     | array of Field | yes      | Must have at least one field                         |

Each field:

| Field  | Type    | Required | Description          |
|--------|---------|----------|----------------------|
| `name` | string  | yes      | Field name           |
| `type` | TypeRef | yes      | Field type           |
| `doc`  | string  | no       | Documentation string |

### Struct example

```yaml
version: "0.9.0"
modules:
  - name: geometry
    structs:
      - name: Point
        doc: "A 2D point in space"
        fields:
          - name: x
            type: f64
            doc: "X coordinate"
          - name: "y"
            type: f64
            doc: "Y coordinate"

      - name: Rect
        fields:
          - name: origin
            type: Point
          - name: width
            type: f64
          - name: height
            type: f64

      - name: Config
        fields:
          - name: timeout
            type: i32
          - name: retries
            type: i32
          - name: label
            type: "string?"

    functions:
      - name: distance
        params:
          - { name: a, type: Point }
          - { name: b, type: Point }
        return: f64

      - name: bounding_box
        params:
          - { name: points, type: "[Point]" }
        return: Rect
```

Struct fields may reference other structs, enums, interfaces, optionals,
lists, or maps, nested to any depth. Iterators and callback interfaces are
not valid field types (see [Type positions](#type-positions)).

A struct crosses the C ABI **by value** as a serialized value buffer: one
`(const uint8_t*, size_t)` pair holding the fields packed in declaration
order. Generators map it to an idiomatic value type (a data class, struct,
or record) with a generated pack and unpack routine; no per-struct C
functions exist. An interface-typed field is encoded as an object token that
carries one strong reference; see [Objects in value buffers](value-buffers.md#objects).

## Enum definitions

Enums define a fixed set of named integer variants. Each variant has an
explicit `value` (`i32`). Define enums under the `enums` key.

### Enum schema

| Field        | Type             | Required | Description                                       |
|--------------|------------------|----------|---------------------------------------------------|
| `name`       | string           | yes      | Enum name (e.g. `Color`)                          |
| `doc`        | string           | no       | Documentation string                              |
| `deprecated` | string           | no       | Deprecation message applied to the generated type |
| `variants`   | array of Variant | yes      | Must have at least one variant                    |

Each variant:

| Field    | Type           | Required | Description                                  |
|----------|----------------|----------|----------------------------------------------|
| `name`   | string         | yes      | Variant name (e.g. `Red`)                    |
| `value`  | i32            | yes      | Integer discriminant                         |
| `doc`    | string         | no       | Documentation string                         |
| `fields` | array of Field | no       | Associated data; makes the enum a *sum type* |

### Enum example

```yaml
version: "0.9.0"
modules:
  - name: contacts
    enums:
      - name: ContactType
        doc: "Category of contact"
        variants:
          - name: Personal
            value: 0
            doc: "Friends and family"
          - name: Work
            value: 1
            doc: "Professional contacts"
          - name: Other
            value: 2

    functions:
      - name: count_by_type
        params:
          - { name: contact_type, type: ContactType }
        return: i32
```

Variant values must be unique within an enum, and variant names must be
unique within an enum.

### Rich (algebraic) enums: sum types

When one or more variants declare `fields`, the enum becomes a *rich* enum:
an algebraic sum type whose variants carry associated data (like a Rust
`enum` or a Swift `enum` with associated values). A *unit* variant (no
`fields`) and a *data* variant may coexist in the same enum.

```yaml
version: "0.9.0"
modules:
  - name: shapes
    enums:
      - name: Shape
        doc: "An algebraic shape"
        variants:
          - name: Empty
            value: 0
          - name: Circle
            value: 1
            fields:
              - { name: radius, type: f64 }
          - name: Rectangle
            value: 2
            fields:
              - { name: width, type: f32 }
              - { name: height, type: f32 }
    functions:
      - name: area
        params:
          - { name: shape, type: Shape }
        return: f64
```

A plain C-style enum crosses the ABI by value as an `int32_t`. A rich enum
also crosses by value, but as a serialized value buffer: an `i32` tag (the
variant's declared `value`) followed by the active variant's fields in
declaration order, in one `(const uint8_t*, size_t)` pair. No per-enum C
functions are generated; each backend maps the enum to its idiomatic sum
type (a Rust-style enum, a Swift enum with associated values, a sealed class
hierarchy, a tagged union class) with a generated pack and unpack routine.
See the [Value Buffer Protocol](value-buffers.md) for the encoding.

A variant `fields` entry uses the same shape as a struct field (`name`,
`type`, `doc`) and obeys the positional rules of a buffered slot: no
iterators and no callback interfaces. Field names must be unique within a
variant.

Only a C-style enum (no variant carries fields) is a member of the *direct*
family: it may be a map key and may be returned from a callback-interface
method. A rich enum is a buffered value like a struct.

## Interfaces

An interface is a first-class object type: a stateful resource with identity
and behavior, declared under the `interfaces` key of a module. Where a struct
models a plain data record with fields, an interface models something you
*hold and operate on*: a store, a session, a connection. The object lives
behind the FFI boundary and crosses it as an opaque, reference-counted
pointer; consumers see a real class (or the target's closest analogue) whose
constructors, methods, and statics call into the producer.

### Interface schema

| Field          | Type                 | Required | Description                                         |
|----------------|----------------------|----------|-----------------------------------------------------|
| `name`         | string               | yes      | Interface type name (e.g. `Store`)                  |
| `doc`          | string               | no       | Documentation string                                |
| `deprecated`   | string               | no       | Deprecation message applied to the generated class  |
| `constructors` | array of Constructor | no       | Static functions returning a new instance           |
| `methods`      | array of Function    | no       | Instance methods                                    |
| `statics`      | array of Function    | no       | Static functions namespaced under the interface     |

An interface must declare at least one member, and constructor, method, and
static names share one namespace per interface (no duplicates across the
three lists).

Each constructor:

| Field    | Type           | Required | Description                                                   |
|----------|----------------|----------|---------------------------------------------------------------|
| `name`   | string         | yes      | Constructor identifier (e.g. `open`)                          |
| `params` | array of Param | no       | Input parameters                                              |
| `doc`    | string         | no       | Documentation string                                          |
| `throws` | bool           | no       | Report a typed domain error on failure (default `false`)      |

A constructor implicitly returns a new instance of its interface, so it
declares no `return` field, and it may not be `async` (expose an async
static factory returning the interface instead). A constructor named `new`
becomes the canonical constructor where the target language has one (Swift
`init`, Python `__init__`); every other constructor becomes a static factory
method.

Methods and statics use the full [Function schema](#function), including
`throws`, `async`, `cancellable`, and `deprecated`. A method receives the
instance implicitly; it does not declare a `self` parameter. A static takes
no instance at all.

### Reference counting and lifecycle

Objects are **reference counted by the producer**. Every interface receives
two implicit lifecycle symbols, `{tag}_clone` and `{tag}_destroy`; you never
declare either in the IDL. A pointer to an object is a strong reference:
`_clone` returns a second strong reference to the same object (the pointer
value is identical), `_destroy` releases one, and the object is dropped when
the last reference goes.

Every generated wrapper owns exactly one strong reference and releases it
deterministically through the language's natural disposal hook (C++
destructor, Swift `deinit`, Kotlin `close()` and `AutoCloseable`, Python
`close()` and context managers, .NET `IDisposable`, Ruby `AutoPointer`, Go
`Close()`, Dart `close()`, JavaScript `close()` and `Symbol.dispose`), with a
finalizer or `Cleaner` backstop where the runtime has one. Because the count
lives in the producer, the same object can be held by any number of
wrappers, stored inside records and collections, retained by the producer,
and outlive the call that produced it.

Ownership follows the reference direction:

| Position                                    | Direction            | Rule                                                                    |
|---------------------------------------------|----------------------|-------------------------------------------------------------------------|
| parameter (`Store`, `Store?`)               | consumer to producer | borrowed for the call; the producer clones if it retains the object     |
| return, async result, iterator element      | producer to consumer | one strong reference transfers; the wrapper adopts it                   |
| callback-interface method parameter         | producer to consumer | one strong reference transfers; the consumer adopts it                  |
| inside a value buffer (record field, list element, map value, optional) | either | the object token carries one strong reference; the reader adopts it |

The normative statement of these rules is in the
[C ABI Contract](abi.md#objects-interfaces).

### Where interface types may appear

An interface name is a valid `TypeRef` in **every** position except a map
key: parameters, returns, optionals (`Store?`), lists (`[Store]`), map
values (`{string:Store}`), struct fields, rich-enum variant fields, error
payload fields, iterator elements (`iter<Store>`), async returns, and
callback-interface method parameters. `Store?` at the top level of a
parameter or return is a nullable pointer (null means none); inside a value
buffer it uses the ordinary optional flag byte followed by the object token.

The one rejection is the map key: no target can hash an object by identity
in a way that survives the ABI. The validator reports it as
`InterfaceInInvalidPosition` (alongside `InvalidMapKey`):

```yaml
# rejected: InterfaceInInvalidPosition
version: "0.9.0"
modules:
  - name: kv
    interfaces:
      - name: Store
        methods:
          - { name: count, return: i64 }
    functions:
      - name: index_by_store
        params:
          - { name: stores, type: "{Store:i32}" }
```

### Interface example

A trimmed version of the `kvstore` sample's `Store` interface, showing an
object in each of the positions above:

```yaml
version: "0.9.0"
modules:
  - name: kv
    errors:
      name: KvError
      codes:
        - { name: KeyNotFound, code: 1001, message: "key not found" }
        - { name: IoError, code: 1004, message: "I/O failure" }
    structs:
      - name: StoreInfo
        doc: A named view of a store; `store` carries a strong reference
        fields:
          - { name: label, type: string }
          - { name: store, type: Store }
          - { name: mirror, type: "Store?" }
          - { name: count, type: i64 }
    interfaces:
      - name: Store
        doc: An embedded key-value store owning its entries
        constructors:
          - name: open
            doc: Open (or create) a store backed by the given filesystem path
            params:

            throws: true
        methods:
          - name: get
            doc: Look up a value by key
            params:
              - { name: key, type: string }
            return: bytes

          - name: count

            return: i64
          - name: share
            doc: A second reference to this same store
            return: Store

            doc: Whichever of `self` and `other` holds more entries
            params:
              - { name: other, type: "Store?" }
            return: "Store?"

            params:
```

### C ABI lowering

An interface lowers to an opaque struct tag, one C symbol per member, and
the two lifecycle symbols. Constructors return an owned reference; methods
take a leading `const {tag}* self` slot before their declared parameters;
statics take no `self`; a top-level object parameter is a borrowed
`const {tag}*`; an object return is an owned `{tag}*`; and a list or record
that carries objects is an ordinary value buffer whose object tokens each
carry one reference. The header the C generator emits for the example above:

```c
typedef struct weaveffi_kv_Store weaveffi_kv_Store;

/* Constructor: returns one strong reference. */
WEAVEFFI_API weaveffi_kv_Store* weaveffi_kv_Store_open(const char* path, weaveffi_error* out_err);

/* Statics: no self slot. `[Store]` in and out is a value buffer of object tokens. */
WEAVEFFI_API const uint8_t* weaveffi_kv_Store_open_many(const uint8_t* paths_ptr, size_t paths_len, size_t* out_len, weaveffi_error* out_err);
WEAVEFFI_API int64_t weaveffi_kv_Store_total_count(const uint8_t* stores_ptr, size_t stores_len, const uint8_t* extra_ptr, size_t extra_len, weaveffi_error* out_err);

/* Methods: an implicit leading self slot. */
WEAVEFFI_API const uint8_t* weaveffi_kv_Store_get(const weaveffi_kv_Store* self, const char* key, size_t* out_len, weaveffi_error* out_err);
WEAVEFFI_API int64_t weaveffi_kv_Store_count(const weaveffi_kv_Store* self, weaveffi_error* out_err);
WEAVEFFI_API weaveffi_kv_Store* weaveffi_kv_Store_share(const weaveffi_kv_Store* self, weaveffi_error* out_err);
WEAVEFFI_API weaveffi_kv_Store* weaveffi_kv_Store_larger(const weaveffi_kv_Store* self, const weaveffi_kv_Store* other, weaveffi_error* out_err);
WEAVEFFI_API const uint8_t* weaveffi_kv_Store_describe(const weaveffi_kv_Store* self, const char* label, const weaveffi_kv_Store* mirror, size_t* out_len, weaveffi_error* out_err);

/* Implicit lifecycle symbols. */
WEAVEFFI_API weaveffi_kv_Store* weaveffi_kv_Store_clone(const weaveffi_kv_Store* self);
WEAVEFFI_API void weaveffi_kv_Store_destroy(weaveffi_kv_Store* self);
```

Async and iterator-returning members follow the same shapes as free
functions (the async launcher and the iterator handle simply carry the
`self` slot). Free functions and interface members share the module's C
symbol namespace, so a free function named `Store_get` would collide with a
`get` method on an interface `Store`, and a free function named
`Store_clone` would collide with the implicit lifecycle symbol; the
validator rejects both as `AbiSymbolCollision`.

On the Rust side an interface is a `#[weaveffi::interface]` struct that
must be `Send + Sync`; constructors return `Self` or `Arc<Self>`, methods take
`&self` or `self: Arc<Self>`, and an object in any other position is an
`Arc<T>`. See [The Rust Producer Macro](../guides/producer-macro.md).

## Callback interfaces

A callback interface is the inverse of an interface: a set of methods the
**consumer** implements and the **producer** calls. Declare one under the
`callback_interfaces` key of a module, then take it as a parameter wherever
the producer needs to call back into the host language: an event
subscriber, an eviction observer, a progress reporter. The consumer passes
an implementation (a class instance, a closure record, a trait object); the
producer keeps it alive as long as it needs to and may call its methods any
number of times, from any thread.

### Callback interface schema

| Field        | Type              | Required | Description                                                          |
|--------------|-------------------|----------|----------------------------------------------------------------------|
| `name`       | string            | yes      | Callback interface type name (e.g. `EvictionListener`)               |
| `doc`        | string            | no       | Documentation string                                                 |
| `deprecated` | string            | no       | Deprecation message applied to the generated type                    |
| `methods`    | array of Function | yes      | Methods the consumer implements, in vtable order; must be non-empty  |

Each method uses the [Function schema](#function) with these restrictions,
each enforced by the validator as `InvalidCallbackMethod`:

- **Synchronous.** `async: true` and `cancellable: true` are rejected.
- **Never `throws`.** A method has no typed error channel. A consumer
  implementation that raises is reported to the original caller as the
  runtime's foreign error (`-4`); see below.
- **Direct returns only.** A method returns nothing, a scalar (`i8`..`u64`,
  `f32`, `f64`), `bool`, or a C-style enum. Strings, bytes, records, rich
  enums, optionals, lists, maps, and objects can't be returned, because no
  producer-owned allocation may flow back from the consumer.
- **Parameters may be anything except another callback interface or an
  iterator.** Strings, bytes, records, enums, optionals, lists, maps, and
  interface objects are all valid; objects transfer a strong reference to
  the consumer.

### Where callback interfaces may appear

A callback interface is valid **only** as a bare top-level parameter of a
function, constructor, method, or static. It can't be returned, wrapped in an
optional or collection (`Listener?`, `[Listener]`), used as a struct or
variant field, or passed to another callback-interface method. The
validator reports every other position as
`CallbackInterfaceInInvalidPosition`:

```yaml
# rejected: CallbackInterfaceInInvalidPosition
version: "0.9.0"
modules:
  - name: events
    callback_interfaces:
      - name: Listener
        methods:
          - { name: on_event, params: [{ name: id, type: i64 }] }
    functions:
      - name: maybe_listen
        params:
          - { name: listener, type: "Listener?" }
      - name: current_listener
        return: Listener
```

### Callback interface example

A trimmed version of the `events` sample: a `Subscriber` the consumer
implements, an `EventBus` object that retains subscribers, and an object
(`EventBus`) handed back to the consumer through a callback method:

```yaml
version: "0.9.0"
modules:
  - name: events
    doc: A publish/subscribe event bus driven by a consumer-implemented subscriber.
    enums:
      - name: Delivery
        doc: How a subscriber wants to be told about a message.
        variants:
          - { name: Accept, value: 0 }
          - { name: Skip, value: 1 }
          - { name: AcceptAndStop, value: 2 }
    structs:
      - name: Message
        fields:
          - { name: seq, type: i64 }
          - { name: topic, type: string }
          - { name: text, type: string }
          - { name: tags, type: "[string]" }
    callback_interfaces:
      - name: Subscriber
        doc: A consumer-implemented subscriber.
        methods:
          - name: route
            doc: Decide how the bus should treat `topic` for this subscriber.
            params:
              - { name: topic, type: string }
            return: Delivery
          - name: on_message
            doc: Receive an accepted message; returns the running count.
            params:
              - { name: message, type: Message }
            return: i64
          - name: on_attached
            doc: Receive the bus itself; the consumer adopts the reference.
            params:
              - { name: bus, type: EventBus }
    interfaces:
      - name: EventBus
        constructors:
          - name: new
        methods:
          - name: subscribe
            params:
              - { name: subscriber, type: Subscriber }
            return: i64
          - name: publish
            params:
              - { name: topic, type: string }
              - { name: text, type: string }
              - { name: tags, type: "[string]" }
            return: i64
    functions:
      - name: route_once
        doc: Ask `subscriber` how it would route `topic` without a bus.
        params:
          - { name: subscriber, type: Subscriber }
          - { name: topic, type: string }
        return: Delivery
```

### C ABI lowering

A callback interface lowers to a vtable type and no exported symbols. The
vtable has one function-pointer entry per method, in declaration order, and
a trailing `free`. Every entry takes the consumer's `void* ctx` first and a
`weaveffi_error* out_err` last. A parameter of the type lowers to two slots,
`void* {name}_ctx` and `const {tag}_vtable* {name}_vtable`. The header for
the example above:

```c
typedef struct weaveffi_events_Subscriber_vtable {
    weaveffi_events_Delivery (*route)(void* ctx, const char* topic, weaveffi_error* out_err);
    int64_t (*on_message)(void* ctx, const uint8_t* message_ptr, size_t message_len, weaveffi_error* out_err);
    void (*on_attached)(void* ctx, weaveffi_events_EventBus* bus, weaveffi_error* out_err);
    void (*free)(void* ctx);
} weaveffi_events_Subscriber_vtable;

WEAVEFFI_API int64_t weaveffi_events_EventBus_subscribe(const weaveffi_events_EventBus* self, void* subscriber_ctx, const weaveffi_events_Subscriber_vtable* subscriber_vtable, weaveffi_error* out_err);
WEAVEFFI_API weaveffi_events_Delivery weaveffi_events_route_once(void* subscriber_ctx, const weaveffi_events_Subscriber_vtable* subscriber_vtable, const char* topic, weaveffi_error* out_err);
```

Note the `on_attached` slot: an object parameter of a callback method is a
mutable `{tag}*`, not the borrowed `const {tag}*` of an ordinary parameter,
because the producer transfers one strong reference that the consumer adopts.
Strings, bytes, and buffers arriving in a callback method are borrowed for
the duration of the call; the consumer copies or decodes them before
returning.

The consumer owns `ctx` (generated wrappers use a handle-table key that
keeps the implementing object alive) and one process-wide static vtable per
callback interface. The producer may call any entry from any thread until it
calls `free(ctx)` exactly once, after which it never touches `ctx` again. A
consumer implementation that raises calls
`weaveffi_error_set(out_err, -4, message)` instead of letting the exception
unwind through C; the producer aborts the call it was making and the
original caller observes `FOREIGN_ERROR_CODE` with the consumer's message.
The full contract, including the Rust-side unwinding behavior producers
must tolerate, is in the [C ABI Contract](abi.md#callback-interfaces).

On the Rust side a callback interface is a `#[weaveffi::callback_interface]`
trait with `Send + Sync` supertraits and `&self` methods; producers accept
one as `Arc<dyn Name>`.

## Optional types

Append `?` to any type to make it optional (nullable).

| Syntax     | Meaning                                                                   |
|------------|---------------------------------------------------------------------------|
| `string?`  | Optional string                                                           |
| `i32?`     | Optional i32                                                              |
| `Contact?` | Optional struct                                                           |
| `Color?`   | Optional enum                                                             |
| `Store?`   | Optional interface (a nullable pointer at the top level, an optional token inside a buffer) |

### Optional example

```yaml
version: "0.9.0"
modules:
  - name: contacts
    structs:
      - name: Contact
        fields:
          - { name: id, type: i64 }
          - { name: name, type: string }
          - { name: email, type: "string?" }
          - { name: nickname, type: "string?" }
    functions:
      - name: find_contact
        params:
          - { name: id, type: i64 }
        return: "Contact?"
        doc: "Returns null if no contact exists with the given id"

      - name: update_email
        params:
          - { name: id, type: i64 }
          - { name: email, type: "string?" }
```

> **YAML note:** Quote optional types like `"string?"` and `"Contact?"` to
> prevent the YAML parser from treating `?` as special syntax.

Every optional except `Interface?` crosses the ABI as a value buffer (a flag
byte, then the value when present). `Interface?` stays a nullable object
pointer so the common "maybe an object" shape needs no encoding step.

```yaml
version: "0.9.0"
modules:
```

## Map types

Wrap a key-value pair in `{K:V}` braces to declare a map (dictionary,
associative array). Keys must be scalar, `bool`, `string`, or C-style enum
types; values may be any valid `TypeRef` other than an iterator or a
callback interface.

| Syntax             | Meaning                          |
|--------------------|----------------------------------|
| `{string:i32}`     | Map from string to i32           |
| `{string:Contact}` | Map from string to struct        |
| `{i32:string}`     | Map from i32 to string           |
| `{string:[i32]}`   | Map from string to list of i32   |
| `{string:Store}`   | Map from string to object        |

### Map example

```yaml
version: "0.9.0"
modules:
  - name: maps
    structs:
      - name: Contact
        fields:
          - { name: id, type: i64 }
          - { name: name, type: string }
          - { name: email, type: "string?" }
    functions:
      - name: update_scores
        params:
          - { name: scores, type: "{string:i32}" }
        return: bool
        doc: "Update player scores by name"

      - name: get_contacts
        return: "{string:Contact}"
        doc: "Returns a map of name to Contact"

      - name: merge_tags
        params:
          - { name: current, type: "{string:string}" }
          - { name: additions, type: "{string:string}" }
        return: "{string:string}"
```

> **YAML note:** Quote map types like `"{string:i32}"` because YAML
> interprets bare `{...}` as an inline mapping.

### C ABI convention

Maps cross the FFI boundary **by value** as a serialized value buffer: a
`u32` entry count followed by alternating keys and values, all in one
`(const uint8_t*, size_t)` pair. A map parameter `{K:V}` named `m` expands
to two C parameters:

```c
const uint8_t* m_ptr, size_t m_len
```

A map return comes back as a `const uint8_t*` return value plus a
`size_t* out_len` out-parameter, freed by the consumer with
`weaveffi_free_bytes`. For example, `update_scores(scores: {string:i32})`
generates:

```c
WEAVEFFI_API bool weaveffi_maps_update_scores(const uint8_t* scores_ptr, size_t scores_len, weaveffi_error* out_err);
```

See the [Value Buffer Protocol](value-buffers.md) for the encoding and
ownership rules.

### Key type restrictions

Only the integers, `f32`, `f64`, `bool`, `string`, and C-style enum types
are valid map keys, so every target language can use the key in its native
dictionary idiom. The validator rejects structs, rich enums, interfaces,
lists, maps, optionals, and `bytes` as key types with `InvalidMapKey`:

```yaml
# rejected: InvalidMapKey
version: "0.9.0"
modules:
  - name: maps
    functions:
      - name: by_blob
        params:
          - { name: index, type: "{bytes:i32}" }
```

## Nested types

Optional, list, and map modifiers compose freely and nest to any depth,
because every composite serializes into one value buffer:

| Syntax           | Meaning                                            |
|------------------|----------------------------------------------------|
| `[Contact?]`     | List of optional contacts (items may be null)      |
| `[i32]?`         | Optional list of i32 (the entire list may be null) |
| `[string?]`      | List of optional strings                           |
| `{string:[i32]}` | Map from string to list of i32                     |
| `{string:i32}?`  | Optional map (the entire map may be null)          |
| `{string:[Store]}` | Map from string to list of objects               |

### Nested type example

```yaml
version: "0.9.0"
modules:
  - name: nested
    structs:
      - name: Contact
        fields:
          - { name: id, type: i64 }
    functions:
      - name: search
        params:
          - { name: query, type: string }
        return: "[Contact?]"
        doc: "Returns a list where some entries may be null (redacted)"

      - name: get_scores
        params:
          - { name: user_id, type: i64 }
        return: "[i32]?"
        doc: "Returns null if user has no scores, otherwise a list"

      - name: bulk_update
        params:
          - { name: emails, type: "[string?]" }
        return: i32
```

The parser evaluates type syntax outside-in: `[Contact?]` is parsed as
`List(Optional(Contact))`, while `[Contact]?` is parsed as
`Optional(List(Contact))`. Nesting deeper than three levels passes
validation but emits the `DeepNesting` warning under `--warn`.

## Iterator types

Wrap a type in `iter<T>` to declare a lazy iterator over values of type `T`.
Unlike `[T]` (which materializes the full list), iterators yield elements
one at a time and are suitable for large or streaming result sets.

| Syntax          | Meaning                                   |
|-----------------|-------------------------------------------|
| `iter<i32>`     | Iterator over i32 values                  |
| `iter<string>`  | Iterator over strings                     |
| `iter<Contact>` | Iterator over structs                     |
| `iter<Store>`   | Iterator over objects (one reference each) |

### Iterator example

```yaml
version: "0.9.0"
modules:
  - name: streaming
    structs:
      - name: Contact
        fields:
          - { name: id, type: i64 }
    functions:
      - name: scan_entries
        params:
          - { name: prefix, type: string }
        return: "iter<Contact>"
        doc: "Lazily iterates over matching contacts"
```

Laziness is part of the binding contract, not just the C ABI shape. Every
generated wrapper surfaces `iter<T>` as its language's native lazy iteration
idiom: an `iter.Seq` in Go (`iter.Seq2` when the function throws), a
`Sequence` in Swift, an input-iterator range in C++, an iterator in Python,
an `Enumerator` in Ruby, an `IEnumerable<T>` in C#, an `Iterable<T>` in
Dart, an iterable in JavaScript, and an `Iterator<T>` with `close()` in
Kotlin. The wrapper issues one producer `next` call per consumer step; no
target drains the sequence into a hidden list. The underlying iterator
handle is destroyed exactly once, eagerly on exhaustion or from the
wrapper's disposal idiom when iteration is abandoned early, and errors from
the launch and from each `next` follow the function's error strategy (see
the [Error Handling guide](../guides/errors.md#throws-versus-trap)). The
full pull contract is stated in `weaveffi_core::plan::IteratorProtocol`;
element ownership is covered in the
[Memory and Error Model](memory-error.md#iterators).

Iterators are only valid as the **outermost** return type of a synchronous
callable. The validator rejects an iterator in a parameter, a struct or
variant field, an error payload field, or a callback-method parameter, and a
return type that nests one (`[iter<T>]`, `iter<T>?`, `iter<iter<T>>`), as
`IteratorInInvalidPosition`, and an iterator returned from an `async`
function as `AsyncIteratorReturn`:

```yaml
# rejected: IteratorInInvalidPosition
version: "0.9.0"
modules:
  - name: streaming
    functions:
      - name: consume
        params:
          - { name: items, type: "iter<i32>" }
```

## Nested modules

Modules can contain submodules, enabling hierarchical organization of large
APIs. Nested modules share the same validation rules as top-level modules,
and an error domain declared on a parent module is in scope for every
module nested inside it.

### Nested module example

```yaml
version: "0.9.0"
modules:
  - name: app
    functions:
      - name: init

    modules:
      - name: auth
        interfaces:
          - name: Session
            constructors:
              - name: login
                params:
                  - { name: username, type: string }
                  - { name: password, type: string }
            methods:
              - name: user_id
                return: i64

      - name: data
        structs:
          - name: Record
            fields:
              - { name: id, type: i64 }
              - { name: value, type: string }

        functions:
          - name: get_record
            params:
              - { name: id, type: i64 }
            return: Record
```

C ABI symbols for nested modules use underscores to join the path:
`weaveffi_app_auth_Session_login`, `weaveffi_app_data_get_record`.

### Cross-module type references

Struct, enum, interface, callback interface, and error domain names are
unique across the whole API (the validator rejects two types sharing a bare
name, wherever they are declared, as `DuplicateTypeName`). A bare type name
therefore resolves unambiguously from any module: reference the type by name
and the toolchain qualifies the reference to its owning module internally.
A dot-qualified spelling (`kv.Store`) is also accepted.

For example, a nested `stats` module can take the parent `kv` module's
`Store` interface as a parameter:

```yaml
version: "0.9.0"
modules:
  - name: kv
    errors:
      name: KvError
      codes:
        - { name: IoError, code: 1004, message: "I/O failure" }
    interfaces:
      - name: Store
        constructors:
          - name: open
            params:
              - { name: path, type: string }
            throws: true
        methods:
          - name: count
            return: i64
    modules:
      - name: stats
        structs:
          - name: Stats
            fields:
              - { name: total_entries, type: i64 }
        functions:
          - name: get_stats
            doc: Snapshot the current store statistics
            params:
              - { name: store, type: Store }
            return: Stats
            throws: true
```

The generated bindings spell a cross-module reference with the owning
module's qualification where the target needs one; the C symbol is
`weaveffi_kv_stats_get_stats(const weaveffi_kv_Store* store, ...)`.

## Async and lifecycle annotations

### Async functions

Functions, methods, and statics can be marked as asynchronous. See the
[Async Functions guide](../guides/async.md) for detailed per-target
behavior.

```yaml
version: "0.9.0"
modules:
  - name: net
    errors:
      name: NetError
      codes:
        - { name: Unreachable, code: 1, message: "host unreachable" }
    functions:
      - name: fetch_data
        params:
          - { name: url, type: string }
        return: string
        async: true
        throws: true

      - name: upload_file
        params:
          - { name: path, type: string }
        return: bool
        async: true
        cancellable: true
```

An async function lowers to a launcher `{sym}_async` that returns
immediately and a completion callback typedef `{sym}_callback` that fires
exactly once, from an arbitrary producer thread. A `cancellable` function
adds a `weaveffi_cancel_token*` slot to the launcher before the callback:

```c
typedef void (*weaveffi_net_upload_file_callback)(void* context, weaveffi_error* err, bool result);
WEAVEFFI_API void weaveffi_net_upload_file_async(const char* path, weaveffi_cancel_token* cancel_token, weaveffi_net_upload_file_callback callback, void* context);
```

`async` composes with `throws`: an async function that also declares
`throws: true` delivers its failure as the module's typed domain error
through the target's async idiom (an `async throws` function in Swift, a
rejected promise carrying the typed error in JavaScript, and so on). An
async function without `throws` gets a plain async shape, and a failure can
only be a producer bug. An async function may return an interface object
(the callback adopts one strong reference) or any buffered type; it cannot
return an iterator.

Async void functions (no return type) emit the `AsyncVoidFunction`
validator warning since they are unusual. Constructors can't be `async`
(`AsyncConstructor`); expose an async static factory returning the interface
instead.

The producer runs each future on its configured spawner
(`weaveffi::set_spawner`); the default drives every future on a dedicated
thread. See [Async Functions](../guides/async.md).

### Deprecated declarations

Mark a function, method, static, struct, enum, interface, or callback
interface as deprecated with a migration message:

```yaml
version: "0.9.0"
modules:
  - name: legacy
    functions:
      - name: add_old
        params:
          - { name: a, type: i32 }
          - { name: b, type: i32 }
        return: i32
        deprecated: "Use add_v2 instead"
```

Generators propagate the deprecation message to the target language (a
`WEAVEFFI_DEPRECATED("...")` attribute in C, `@available(*, deprecated)` in
Swift, `@Deprecated` in Kotlin, `warn` in Ruby, and so on). A deprecated
free function also emits the `DeprecatedFunction` warning under `--warn`,
which is informational.

## Type positions

The validator admits each type in the positions below. "Buffered field"
covers struct fields, rich-enum variant fields, and error payload fields;
"callback param" and "callback return" are the parameters and return of a
callback-interface method.

| Type                    | Param | Return | Buffered field | Element of `T?`, `[T]`, `{K:V}` value | Map key | Callback param | Callback return | Notes |
|-------------------------|-------|--------|----------------|----------------------------------------|---------|----------------|-----------------|-------|
| integers, `f32`, `f64`, `bool` | yes | yes | yes           | yes                                    | yes     | yes            | yes             | the *direct* family |
| `string`                | yes   | yes    | yes            | yes                                    | yes     | yes            | no              | |
| `bytes`                 | yes   | yes    | yes            | yes                                    | no      | yes            | no              | |
| C-style enum            | yes   | yes    | yes            | yes                                    | yes     | yes            | yes             | direct family |
| rich enum               | yes   | yes    | yes            | yes                                    | no      | yes            | no              | buffered |
| struct                  | yes   | yes    | yes            | yes                                    | no      | yes            | no              | buffered |
| interface               | yes   | yes    | yes            | yes                                    | no      | yes            | no              | reference counted everywhere |
| callback interface      | yes   | no     | no             | no                                     | no      | no             | no              | bare top-level parameter only |
| `T?`, `[T]`, `{K:V}`    | yes   | yes    | yes            | yes                                    | no      | yes            | no              | buffered; obey the inner type's rules |
| `iter<T>`               | no    | yes    | no             | no                                     | no      | no             | no              | outermost return of a sync callable only |

## Validation

`weaveffi validate <file>` (and every generating command) runs the complete
rule set below and reports **every** violation it finds in one pass, each
with a message, a suggestion, and, when the offending name can be located,
an underlined span in the source. `weaveffi validate --format json` emits
the same diagnostics as machine-readable objects whose `code` field is the
variant name listed in the catalog; `--warn` adds the advisory warnings.

### Rules

Names and uniqueness:

- Module, function, parameter, struct, field, enum, variant, variant field,
  interface, callback interface, callback method, error domain, and error
  code names must be valid
  identifiers (start with a letter or `_`, contain only ASCII alphanumerics
  and `_`) and must not be one of the reserved words `if`, `else`, `for`,
  `while`, `loop`, `match`, `type`, `return`, `async`, `await`, `break`,
  `continue`, `fn`, `struct`, `enum`, `mod`, `use`.
- Names must be unique within their scope: module names among siblings,
  function names within a module, parameter names within a callable, field
  names within a struct or variant, variant names and values within an enum,
  and struct, enum, interface, and callback interface names within a
  module.
- Struct, enum, interface, callback interface, and error domain names must
  be unique across the **whole API**, not just their module: generators emit
  flat per-language type names, and bare-name references resolve API-wide.
- Free functions and interface members share the module's C symbol
  namespace. A free function claims `{name}`; an interface claims
  `{Interface}_{member}` for every member plus `{Interface}_clone` and
  `{Interface}_destroy`. Two declarations lowering to the same symbol are
  rejected.

Shapes:

- Structs must have at least one field. Enums must have at least one
  variant. Interfaces must have at least one constructor, method, or static.
  Callback interfaces must have at least one method.
- Interface members share one namespace per interface. A constructor may
  not declare a `return` type and may not be `async`.
- Callback-interface methods are synchronous (no `async`, no
  `cancellable`), never `throws`, and return nothing or a direct value (a
  scalar, `bool`, or C-style enum).

Types and positions:

- Every user type reference must resolve to a struct, enum, interface, or
  callback interface declared somewhere in the API.
- Map keys must be scalars, `bool`, `string`, or a C-style enum.
- An interface may appear anywhere except as a map key.
- A callback interface may appear only as a bare top-level parameter of a
  function, constructor, static, or method.
- An iterator may appear only as the outermost return type of a
  synchronous callable.

Errors:

- `throws: true` requires an error domain in scope: on the same module or
  an ancestor module.
- Error codes must be positive (`0` means success and negative codes are
  reserved for the runtime) and unique within their domain. Code names must
  be unique within their domain and across every domain in the API.
- The error domain's name must not collide with a function name in the same
  module.

## ABI mapping

A one-screen summary; the [C ABI Contract](abi.md) is normative.

- Scalars, `bool`, and C-style enums pass by value in one slot; C-style
  enums cross as `int32_t`.
- `string` is one `const char*` slot; `bytes` is a
  `const uint8_t* {name}_ptr, size_t {name}_len` pair. Both are borrowed for
  the call as parameters.
- Structs, rich enums, optionals (except `Interface?`), lists, and maps are
  *buffered*: they cross by value as one serialized
  `(const uint8_t* {name}_ptr, size_t {name}_len)` pair, borrowed for the
  duration of the call (see the [Value Buffer Protocol](value-buffers.md)).
- Interfaces cross as `const {tag}*` parameters (borrowed) and `{tag}*`
  returns (one strong reference); `Interface?` is the same slot with null
  meaning none. Every interface has `{tag}_clone` and `{tag}_destroy`.
- Callback interfaces lower to `void* {name}_ctx, const {tag}_vtable* {name}_vtable`.
- Return values are direct scalars except: `string` returns `const char*`
  (freed with `weaveffi_free_string`); `bytes` and every buffered type
  return `const uint8_t*` plus a `size_t* out_len` out-parameter (freed with
  `weaveffi_free_bytes`); `iter<T>` returns an iterator handle with `_next`
  and `_destroy` symbols.
- Every synchronous symbol takes a trailing `weaveffi_error* out_err`
  after all inputs and out-parameters. `_clone` and `_destroy` take none.

## Error domain

A module can declare one error domain: a named set of symbolic error codes
its fallible callables report. The domain generates a *typed* error
construct in every target language (an error enum in Swift, an exception
class hierarchy in Python, sealed exception subclasses in Kotlin, and so
on), so consumers catch and match on the codes you declared rather than on
raw integers.

### Error domain schema

| Field   | Type          | Required | Description                                                                 |
|---------|---------------|----------|-----------------------------------------------------------------------------|
| `name`  | string        | yes      | Domain name, used to name the generated error type (e.g. `KvError`)         |
| `codes` | array of Code | yes      | The named codes belonging to this domain                                    |

Each code:

| Field     | Type           | Required | Description                                                                                        |
|-----------|----------------|----------|----------------------------------------------------------------------------------------------------|
| `name`    | string         | yes      | Code name, lowered to a case or subclass on the generated error type (e.g. `KeyNotFound`)          |
| `code`    | i32            | yes      | Stable numeric value carried across the C ABI; must be positive                                    |
| `message` | string         | yes      | Default human-readable message                                                                     |
| `doc`     | string         | no       | Documentation string                                                                               |
| `fields`  | array of Field | no       | Structured payload fields this error carries (see [Structured error payloads](#structured-error-payloads)) |

PascalCase code names (`KeyNotFound`, `StoreFull`) are the convention: each
generator re-cases them into its own idiom (see
[Naming and Package Conventions](naming.md#error-domains-and-codes)).

### Structured error payloads

A code may declare `fields:` using the same shape as struct fields (`name`,
`type`, `doc`). When a matching error is raised, those fields are serialized
into the `weaveffi_error` struct's `payload_ptr`/`payload_len` slots in the
value-buffer format, and each generator decodes them into properties of the
raised exception or returned error value, keyed by the field names:

```yaml
version: "0.9.0"
modules:
  - name: kv
    errors:
      name: KvError
      codes:
        - name: KeyNotFound
          code: 1001
          message: "key not found"
          fields:
            - { name: key, type: string }
            - { name: attempts, type: i32 }
    functions:
      - name: lookup
        params:
          - { name: key, type: string }
        return: bytes
        throws: true
```

Payload fields obey the buffered positional rules: no iterators and no
callback interfaces (an interface object is allowed and carries a
reference like any other object token). A code without `fields` leaves the
payload slots null. See the
[Value Buffer Protocol](value-buffers.md#structured-errors) for the wire
format and freeing rules.

### Opting in with `throws`

Declaring a domain reserves the codes; a function, method, static, or
constructor joins the typed error path by declaring `throws: true`:

```yaml
version: "0.9.0"
modules:
  - name: contacts
    errors:
      name: ContactsError
      codes:
        - { name: InvalidName, code: 1, message: "name must not be empty" }
        - { name: NotFound, code: 2, message: "contact not found" }
    functions:
      - name: get_contact
        params:
          - { name: id, type: i64 }
        return: string
        throws: true

      - name: count_contacts
        return: i32
```

A throwing callable surfaces in each target's error idiom (`throws` in
Swift, `raise` in Python, `(T, error)` in Go, exceptions elsewhere), and the
error it delivers is the domain type: the numeric code maps to the matching
declared case. A callable **without** `throws` (like `count_contacts`
above) has a plain signature at the idiomatic surface; it cannot report a
domain error, and a failure there can only be a producer bug, which
surfaces as a generic branded error or a trap rather than a typed error.
See the [Error Handling guide](../guides/errors.md) for the full model,
including panic behavior.

The domain is in scope for its module **and every module nested inside
it**, so a domain declared on a parent module serves the whole subtree.
Declaring `throws: true` with no domain in scope is a validation error
(`ThrowsWithoutErrorDomain`):

```yaml
# rejected: ThrowsWithoutErrorDomain
version: "0.9.0"
modules:
  - name: contacts
    functions:
      - name: get_contact
        params:
          - { name: id, type: i64 }
        return: string
        throws: true
```

### Validation

- Codes must be positive: `0` means success, and the negative range is
  reserved for the runtime (`-1` generic error, `-2` producer panic, `-3`
  marshalling failure, `-4` foreign callback error).
- Numeric codes must be unique within a domain.
- Code names must be unique within a domain **and across every domain in
  the API**: backends with flat namespaces derive one error class or
  constant per code, so two domains both declaring `NotFound` would
  collide. Qualify one of them (e.g. `OrderNotFound`).
- The domain name must not collide with a function name in the same module,
  and it shares the API-wide type namespace with struct, enum, interface,
  and callback interface names.

## Documentation comments

Every IR element accepts an optional `doc:` field. WeaveFFI propagates that
text into the generated bindings using each language's native doc-comment
syntax. Multi-line strings (use YAML's `|` block form) are preserved across
the boundary; single-line strings collapse to a one-liner where the target
syntax allows.

Supported sites:

- `Module.doc`
- `Function.doc`, `Param.doc`
- `InterfaceDef.doc`, plus each of its constructors, methods, and statics
  (interface members use the function schema, so they carry `Function.doc`
  and `Param.doc`)
- `CallbackInterfaceDef.doc`, plus each of its methods and their parameters
- `StructDef.doc`, `StructField.doc`
- `EnumDef.doc`, `EnumVariant.doc`
- `ErrorCode.doc`

Per-target syntax:

| Target            | Comment syntax                                          | Param docs                                                |
|-------------------|---------------------------------------------------------|-----------------------------------------------------------|
| C / C++           | `/** ... */` directly above the declaration             | not emitted                                               |
| Swift             | `/// ...` per line                                      | `/// - Parameter name: ...`                               |
| Kotlin            | `/** ... */` KDoc block                                 | `@param name ...` inside the KDoc block                   |
| TypeScript (Node) | `/** ... */` JSDoc                                      | `@param name ...`                                         |
| TypeScript (Wasm) | `/** ... */` JSDoc                                      | `@param name ...`                                         |
| Python            | `"""..."""` first statement; `# ...` above C ABI binds  | NumPy-style `Parameters` section in the wrapper docstring |
| .NET (C#)         | `/// <summary>...</summary>` XML doc                    | `/// <param name="name">...</param>`                      |
| Dart              | `/// ...`                                               | not emitted                                               |
| Go                | `// SymbolName ...` per Go's convention                 | trailing `// Parameters:` block                           |
| Ruby              | `# ...` lines above the `def`                           | `# @param name [Object] ...`                              |

Example IDL:

```yaml
version: "0.9.0"
modules:
  - name: docs
    doc: Document tracking
    structs:
      - name: Document
        doc: |
          Represents a single document tracked by the system.

          Documents are persisted to disk and exposed via the public API.
        fields:
          - { name: id, type: i64, doc: Stable opaque identifier }
          - { name: title, type: string, doc: Human-readable title }
    functions:
      - name: create_document
        doc: Create a brand new document
        params:
          - { name: title, type: string, doc: Human-readable title }
        return: Document
```

All eleven generators emit doc comments before every documented
declaration; absent or empty `doc:` fields produce no extra output, so the
feature is fully opt-in.
